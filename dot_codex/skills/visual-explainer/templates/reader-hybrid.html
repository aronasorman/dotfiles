How the queue keeps writes safe

Why a durable backlog turns a lost write into a delayed one, and what it costs to run.

The problem in one paragraph

A write arrives faster than the store can accept it. Without somewhere to park the write, the request either blocks until the store catches up or fails outright, and the caller cannot tell which writes survived. A durable backlog turns that choice into a delay instead of a loss.

The cost is that the backlog becomes a component with its own failure modes. It can fill, it can reorder, and it can hand the same item to two workers. Everything below is about those three risks, and usually only the first one shows up in practice.

Three ways to hold the backlog

Each option keeps the same backlog; they differ in what survives a restart and what you have to operate.

  • In-process buffer

    An in-memory list inside the writer, drained by a background loop.

    Durability
    None. A restart loses the backlog.
    Operational cost
    Nothing to run or monitor.
    Fits when
    Writes are reproducible and the caller can retry.

  • Table in the store

    A pending-writes table in the same database, polled by workers.

    Durability
    Same guarantees as the data itself.
    Operational cost
    One more table and a poll interval to tune.
    Fits when
    The store has headroom and you want one backup to restore.

  • Dedicated broker

    A separate queue service between the writer and the workers.

    Durability
    Configurable, and independent of the store.
    Operational cost
    A service to run, patch, and watch.
    Fits when
    Several producers and consumers need the same backlog.

What happens to one write

  1. Caller to gateway

    The caller submits a write and waits only for the gateway to acknowledge that it has been recorded.

  2. Gateway to backlog

    The gateway appends the write with a generated key, then returns that key so the caller can ask about it later.

  3. Worker to store

    A worker claims the item, applies it to the store, and marks it done. Claims expire, so a worker that dies mid-flight releases its item.

  4. Worker to backlog

    A write that fails repeatedly moves to a parking area with its error attached, rather than blocking the items behind it.

Where this usually goes wrong

Expiring claims mean an item can be applied twice, so each write needs to be safe to repeat. That is a property of the write, not of the queue, and it is the part most often left until after the first incident.
